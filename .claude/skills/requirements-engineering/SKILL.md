# 요구사항 공학(Requirements Engineering) 스킬

이 스킬은 ISO 26262(기능안전)와 Automotive SPICE 4.1(SYS.2 시스템 요구사항 분석, SWE.1 소프트웨어 요구사항 분석)을 동시에 만족하는 요구사항을 작성·점검·추적하기 위한 방법론을 정의한다.

## 0. 템플릿 우선 원칙

- 요구사항 문서/항목은 **사용자가 제공하는 템플릿을 최우선으로 준수**한다.
- 템플릿이 저장소 내(`templates/`, `docs/templates/` 등)에 존재하는지 먼저 확인한다.
- 템플릿이 없으면 임의로 양식을 확정하지 말고, 사용자에게 템플릿 제공을 요청하거나 "템플릿 미확정, 임시 초안" 임을 명시하고 아래 §1~§7의 최소 항목만 반영한 임시 구조로 작성한다. 템플릿이 도착하면 기존 요구사항을 해당 구조로 재구성한다.

## 1. 요구사항 최소 필수 항목 (템플릿 부재 시 기본 구조)

| 항목 | 설명 |
|---|---|
| ID | 고유 식별자 (예: `REQ-SYS-0001`, `REQ-SW-0001`) |
| 제목 | 요구사항 요약 |
| 유형 | 기능(Functional) / 비기능(Non-Functional) |
| 출처(Source) | 상위 요구사항 ID, 이해관계자 요구, 안전목표(Safety Goal) 등 |
| 본문 | §3(명확성 규칙)을 따르는 요구사항 문장 |
| ASIL | 안전 관련 시 QM/A/B/C/D 명시 (ISO 26262-9 근거) |
| 검증기준/방법 | §4·§5 참조 |
| 추적 링크 | 상위/하위 추적 ID (§6) |
| 다이어그램 참조 | 기능 요구사항의 경우 관련 UML/SysML 다이어그램 ID (§2) |
| 상태 | Draft / Reviewed / Approved / Baselined |

## 2. 기능 요구사항 — UML/SysML 다이어그램 표현

기능 요구사항은 텍스트만으로 남기지 않고, 성격에 맞는 다이어그램을 **PlantUML(텍스트 기반, 버전관리 가능)** 로 함께 제공한다.

| 요구사항 성격 | 사용 다이어그램 | 목적 |
|---|---|---|
| 시스템 범위/액터 상호작용 | Use Case Diagram | 액터와 기능 범위 정의 |
| 처리 흐름/알고리즘 | Activity Diagram | 단계별 처리 흐름 표현 |
| 컴포넌트 간 상호작용/메시지 순서 | Sequence Diagram | 인터페이스 간 시나리오 표현 |
| 상태/모드 의존 동작 | State Machine Diagram | 상태 전이 조건과 동작 정의 |
| 요구사항 간 관계(추적성) | SysML Requirement Diagram (`«requirement»`, `«satisfy»`, `«verify»`, `«derive»`, `«refine»`, `«trace»`) | 요구사항-설계-테스트 간 관계 시각화, §6 추적성과 연계 |

- 각 기능 요구사항 문서에는 최소 1개 이상의 다이어그램을 첨부하고, 다이어그램에는 관련 요구사항 ID를 명시적으로 라벨링한다.
- 다이어그램 소스(.puml)는 요구사항 문서와 같은 위치에 버전관리한다.

## 3. 명확성(Clarity) 규칙

- **EARS(Easy Approach to Requirements Syntax) 패턴**을 기본 문장 구조로 사용한다.
  - Ubiquitous: `THE <시스템> SHALL <동작>`
  - Event-driven: `WHEN <트리거>, THE <시스템> SHALL <동작>`
  - State-driven: `WHILE <상태>, THE <시스템> SHALL <동작>`
  - Unwanted behavior: `IF <원치 않는 조건>, THEN THE <시스템> SHALL <동작>`
  - Optional feature: `WHERE <기능 포함 시>, THE <시스템> SHALL <동작>`
- 하나의 요구사항 = 하나의 SHALL 문장(원자성, Atomic). 접속사("그리고", "또는")로 여러 요구를 묶지 않는다.
- 모호어 금지 목록: "적절한", "충분한", "가능한 한", "일반적으로", "빠르게", "사용자 친화적인", "최적화된" 등 — 반드시 측정 가능한 값/조건으로 대체한다.
- 용어집(Glossary)을 두어 동일 용어를 프로젝트 전체에서 동일한 의미로 사용한다(일관성 §7과 연계).

## 4. 비기능 요구사항 — ISO/IEC 25010 기준

비기능 요구사항은 ISO/IEC 25010 품질특성 중 하나 이상에 명시적으로 매핑한다.

| 품질특성 | 하위특성(예) |
|---|---|
| 기능적합성 (Functional Suitability) | 완전성, 정확성, 적절성 |
| 성능효율성 (Performance Efficiency) | 시간반응성, 자원활용성, 용량 |
| 호환성 (Compatibility) | 공존성, 상호운용성 |
| 사용성 (Usability) | 인지성, 학습성, 운용성, 오류방지성, UI심미성, 접근성 |
| 신뢰성 (Reliability) | 성숙성, 가용성, 결함허용성, 회복성 |
| 보안성 (Security) | 기밀성, 무결성, 부인방지성, 책임추적성, 인증성 |
| 유지보수성 (Maintainability) | 모듈성, 재사용성, 분석용이성, 수정용이성, 시험용이성 |
| 이식성 (Portability) | 적응성, 설치성, 대체성 |

- 각 비기능 요구사항은 `[품질특성/하위특성] + 측정 가능한 정량 기준(임계값, 단위)` 형태로 작성한다.
  - 예: "(성능효율성/시간반응성) 시스템은 CAN 메시지 수신 후 10ms 이내에 응답 메시지를 송신해야 한다."

### 4.1 검증방안 — 실행 가능성 필수

- 모든 비기능 요구사항에는 **실행 가능한(Executable/Feasible)** 검증방안을 함께 제시한다.
- 허용 검증방법: **Test(시험)**, **Analysis(분석/계산)**, **Inspection(검사/리뷰)**, **Demonstration(시연)**, **Simulation(시뮬레이션)**.
- 검증방안 작성 시 반드시 포함할 것: 검증방법 종류, 구체적 절차/조건, 사용 도구·환경, 합격판정기준(수치).
- 다음과 같은 **실행 불가능한 검증방안은 금지**한다:
  - 측정 불가능한 주관적 기준으로 판정하는 방안 (예: "사용자가 만족스럽다고 느끼면 통과")
  - 현재 프로젝트에 존재하지 않는 도구/장비/환경을 전제로 하면서 확보 계획이 없는 방안
  - 무한 시간/무한 자원을 요구하는 방안(예: "모든 입력 조합을 전수 시험")
  - 대상 요구사항의 정량 기준과 검증 절차가 논리적으로 맞지 않는 방안(기준값과 측정 방법 불일치)
- 검증방안을 제안하기 전에, 해당 검증이 프로젝트의 실제 도구/환경/일정 내에서 수행 가능한지 확인하고 불확실하면 사용자에게 확인한다.

## 5. 검증기준(기능 요구사항 포함 공통)

- 모든 요구사항(기능/비기능)에는 검증기준(Verification Criteria)을 함께 정의한다(A-SPICE SYS.2/SWE.1 BP5).
- 검증기준은 Pass/Fail을 객관적으로 판정할 수 있어야 한다.

## 6. 양방향 추적성(Bidirectional Traceability) 방안

1. **ID 체계**: `REQ-<레벨>-<일련번호>` (레벨: SYS/SW/HW), 안전요구사항은 `REQ-SYS-SG-xxxx`처럼 안전목표 연계를 표기.
2. **상향 추적(Upstream)**: 각 요구사항의 `출처(Source)` 필드에 상위 요구사항/이해관계자요구/안전목표 ID를 기록.
3. **하향 추적(Downstream)**: 설계 문서, 코드 모듈, 테스트 케이스가 요구사항 ID를 명시적으로 인용(`Satisfies: REQ-SW-0001`, `Verifies: REQ-SW-0001`)하도록 규정.
4. **추적 매트릭스**: `docs/requirements/traceability_matrix.md`(또는 프로젝트 지정 경로)에 요구사항×설계×테스트 매핑 표를 유지하고, 요구사항이 추가/변경/삭제될 때마다 갱신한다.
5. **SysML Requirement Diagram**: §2의 관계(`«satisfy»`, `«verify»`, `«derive»`, `«refine»`, `«trace»`)로 추적 매트릭스를 시각적으로도 표현한다.
6. **고아 요구사항(Orphan) 점검**: 상위/하위 링크가 없는 요구사항은 결함으로 표시하고 보고한다.
7. 이 방안은 문서 작성 시점뿐 아니라 이후 산출물(설계/테스트) 생성·수정 시에도 지속적으로 유지해야 한다 — 요구사항을 다루는 모든 작업에서 추적 매트릭스 갱신을 마지막 단계로 포함한다.

## 7. 일관성(Consistency) 유지

- 동일 용어는 용어집과 동일하게 사용(§3).
- 신규/수정 요구사항 작성 시 기존 요구사항 목록을 검색하여 **중복/모순** 여부를 점검한다(상충되는 값, 상충되는 제약조건).
- ASIL 분해 시 ISO 26262-9 clause 5의 분해 규칙(예: ASIL D → ASIL(D) + ASIL(D), 독립성 검토 필요)을 따르고 임의 하향 조정하지 않는다.
- ID/명명규칙, 문장 패턴(§3 EARS), 단위(SI 단위 등)를 프로젝트 전체에서 통일한다.
- 일관성 점검은 요구사항 세트 전체에 대해 수행하며, 발견된 충돌은 사용자에게 보고하고 임의로 한쪽을 삭제하지 않는다.

## 8. 표준 근거 요약

- **ISO 26262-8 clause 6**: 요구사항은 명확(unambiguous), 이해가능(comprehensible), 원자적(atomic), 내적일관성(internally consistent), 실현가능(feasible), 검증가능(verifiable)해야 한다.
- **ISO 26262-4/6 clause 6**: 시스템/소프트웨어 안전요구사항 명세 시 ASIL, 검증기준, 상위 안전목표와의 연계를 포함해야 한다.
- **A-SPICE SYS.2 / SWE.1**: 이해관계자 요구 파악 → 기능/비기능 요구 도출 → 요구사항 분석(정확성/기술적 실현가능성) → 검증기준 개발 → 영향평가 → 의사소통 → 일관성 및 양방향 추적성 확보.
