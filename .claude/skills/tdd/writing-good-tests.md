# 좋은 테스트 작성하기

> [obra/superpowers](https://github.com/obra/superpowers)의 `writing-good-tests.md`(MIT License, Copyright (c) 2025 Jesse Vincent)를 이 프로젝트(Python/`unittest`)에 맞게 번역·재구성했다.

**언제 참조하나:** 테스트를 새로 작성하거나 수정할 때, mock을 추가할 때, 테스트용 정리(cleanup)/헬퍼 메서드를 추가할 때.

## 개요

테스트는 특정한 깨짐(break)을 잡기 위해 존재한다. 모든 규칙은 두 원칙에서 나온다.

```
1. 모든 테스트는 자신이 잡는 깨짐을 명시한다
2. 모든 테스트는 진짜 대상을 검증한다
```

`tdd` 스킬 §1~§3의 엄격한 RED-GREEN-REFACTOR를 지키면 두 원칙은 자연히 따라온다. 먼저 작성되어 실제 코드에 대해 실패하는 것을 확인한 테스트는 이미 "실패할 수 있음"을 증명했고, 실제 의존성이 느리거나 외부에 있다는 것이 확인된 경우에만 mock으로 대체된다.

## 원칙 1: 깨지는 지점을 명시한다

테스트 본문을 쓰기 전에 답한다: **어떤 프로덕션 코드 변경이 이 테스트를 실패하게 만드는가 — 그리고 그것은 버그인가, 설계 결정인가?** 테스트는 잘못된 분기, 누락된 부작용, 잘못된 인자, 경계 케이스, 깨진 계약을 잡아낼 때 존재 가치가 있다.

**기대값은 독립적으로 도출한다.** 리터럴과 손으로 확인한 픽스처를 사용한다. `want` 값을 리터럴로 나열하는 테이블 기반 테스트가 선호되는 형태다. 검증 대상 코드(또는 그 헬퍼)로 계산한 기대값은 그 코드가 무엇을 하든 항상 통과한다.

```python
# 잘못됨: 같은 빌더로 양쪽을 계산 — 항상 참
expected = buildSearchQuery({"tag": "urgent"})
self.assertEqual(buildSearchQuery({"tag": "urgent"}), expected)

# 올바름: 손으로 도출한 리터럴
self.assertEqual(buildSearchQuery({"tag": "urgent"}), 'tag:"urgent"')
```

**변경감지기(change detector)를 만들지 않는다.** 의도적인 설계 결정(상수값, 정확한 문구, 내부 구조)만 깨뜨릴 수 있는 테스트는 재설계 때마다 실패하고 실제 버그에는 잠들어 있다. 결정 자체가 아니라 그 결정에 의존하는 동작을 검증한다: `self.assertEqual(MAX_RETRIES, 5)`가 아니라 "실패한 호출이 5번 재시도되고 6번째 시도는 일어나지 않는다"를 검증한다.

**행위를 검증하고, 텍스트를 검증하지 않는다.** 스크립트/스킬/설정 파일이 특정 줄을 포함하는지 확인하는 테스트는 "소스가 소스임"만 증명한다. 통제된 입력으로 스크립트를 실제로 실행하고 출력·부작용·종료 코드를 단언한다.

**자신의 코드를, 프레임워크가 아니라.** 코드가 경계에서 맺는 계약(등록하는 라우트, 실행하는 쿼리, 생성하는 페이로드)을 검증한다. 표준 라이브러리/프레임워크의 내부 동작은 그 유지관리자의 테스트 몫이다. 생성자, getter, 상수, 단순 위임(forwarding)은 검증(validate)·정규화·기본값 부여·파생·강제·부작용 중 하나를 수행할 때만 테스트할 가치가 있다 — 그렇지 않으면 그것에 의존하는 첫 번째 관찰 가능한 결과를 검증한다.

### 게이트 함수

```
테스트 본문을 쓰기 전에:
  이 테스트를 실패하게 만드는 프로덕션 코드 변경을 말할 수 있는가?

  말할 수 없다        → 관찰 가능한 행위 중심으로 재설계
  "소스 텍스트가 바뀌었다" → 결과물을 실행하고 그 효과를 단언
  의도적 결정만 깨뜨림  → 변경감지기다; 그 결정에 의존하는 동작을 검증

  기대값이 검증 대상 코드 없이 도출되었는지 확인한다.
  검증 대상 코드나 그 헬퍼를 재사용했다면:
    리터럴이나 손으로 확인한 픽스처로 교체한다
```

## 원칙 2: 진짜 대상을 검증한다

**mock은 그 자체로 단언 대상이 될 수 없다.** mock이 있으면 통과하고 없으면 실패하는 단언은 실제 컴포넌트에 대해 아무것도 말해주지 않는다. 실제 컴포넌트의 동작을 단언한다. mock을 검증하고 있다면 mock을 풀거나 그 단언을 삭제한다.

```python
# 올바름: 실제 동작
self.assertTrue(controller.isTargetReached())

# 잘못됨: mock 존재 여부만 확인
self.assertTrue(mockController.wasCalled)
```

**적절한 수준에서 mock한다.** 실제 메서드를 대체하기 전에 그 부작용을 모두 파악한다. 느리거나 외부에 있는 연산만 mock하고, 테스트가 의존하는 나머지는 실제로 둔다.

```python
# 잘못됨: mock이 중복 검사가 읽는 설정 기록까지 함께 삼켜버림
@mock.patch("tool_catalog.discoverAndCacheTools", return_value=None)

# 올바름: 느린 서버 기동만 mock하고, 설정 기록은 실제로 유지
@mock.patch("mcp_server_manager.MCPServerManager")
```

**대체 객체(double)는 구체적으로 만든다.** 인자, 호출 횟수, 순서가 계약의 일부라면 그것을 단언한다 — 아무 값이나 받는 fake는 아무것도 검증하지 못한다. 성공/오류/잘못된 입력 각 분기마다 별도의 픽스처나 spy를 준다.

**mock 데이터는 실제 구조를 완전히 반영한다.** 테스트가 읽는 필드만이 아니라 실제로 존재하는 모든 필드를 mock한다. 일부만 채운 mock은 다운스트림 코드가 빠진 필드를 읽을 때 조용히 실패한다 — 테스트는 통과하지만 통합은 깨진다.

**정리(cleanup) 코드는 테스트 전용 유틸리티에 둔다.** 테스트에서만 호출되는 메서드를 프로덕션 클래스의 `close()`/`reset()` 같은 메서드로 두지 않는다. "이 메서드는 테스트에서만 호출되는가?", "이 클래스가 이 리소스의 생명주기를 소유하는가?"를 묻는다. 답이 이상하면 테스트 유틸리티로 옮긴다.

**mock이 복잡해지면 실제 컴포넌트를 쓴다.** mock 설정이 테스트 로직보다 커지거나, mock이 실제 컴포넌트의 메서드를 놓치거나, mock이 바뀔 때마다 테스트가 깨진다면 실제 컴포넌트를 사용하는 통합 테스트로 전환한다.

### 게이트 함수

```
mock이나 테스트 헬퍼를 추가하기 전에:
  실제 메서드의 부작용을 나열하고, 테스트가 의존하는 것은 실제로 둔다
  — 느리거나 외부에 있는 수준만 mock한다.

  mock 응답은 실제 구조를 완전히 반영한다.

  테스트에서만 호출되는 메서드는 테스트 유틸리티에 둔다.

  mock 자체를 단언하려 하는가?
    mock을 풀거나 그 단언을 삭제한다.
```

## 테스트는 구현과 함께 완성된다

TDD 사이클(실패하는 테스트 → 최소 구현 → 리팩터링)이 "완료"의 의미다. 그 행위가 필요로 하는 테스트만 만든다 — 자명한 코드와 사람이 읽는 설명 문서는 테스트가 필요 없고, 절차를 지키기 위해 억지로 쓴 테스트는 계속 유지보수 부담만 남긴다.

## 변이 검사(Mutation Check)

마치기 전에 프로덕션 코드를 머릿속으로 변이시켜 본다. 현실적인 변이마다 최소 하나의 테스트가 실패해야 한다:

- 잘못된 상수/인자
- 잘못된 분기 처리
- 누락된 상태 변경/부작용
- 빈 값/기본값 반환
- 0, 빈 값, None, 미인가, 잘못된 형식 입력에 대한 검증 누락

어떤 테스트도 잡지 못하는 변이가 있다면 그 동작은 보호받지 못한 것이거나, 테스트가 항상 통과하는 무의미한(tautological) 테스트라는 뜻이다.

## 빠른 참조

| 상황 | 행동 |
|---|---|
| 테스트를 작성할 때 | 그것이 잡는 깨짐을 명시한다 — 버그, 설계 결정이 아니다 |
| 기대값을 만들 때 | 손으로 도출한다 — 검증 대상 코드로 계산하지 않는다 |
| 스크립트/문서를 테스트할 때 | 실행하거나 그 소비자를 검증한다 — 텍스트를 grep하지 않는다 |
| 의존성 테스트에 손이 갈 때 | 자신의 경계 계약을 검증한다 — 문서화된 내부 동작이 아니다 |
| mock된 요소를 단언하려 할 때 | 실제 컴포넌트를 검증하거나 mock을 푼다 |
| 메서드를 mock하려 할 때 | 그 부작용을 먼저 파악하고, 느리거나 외부에 있는 수준만 mock한다 |
| mock 응답을 만들 때 | 실제 구조를 완전히 반영한다 |
| 테스트 전용 정리가 필요할 때 | 테스트 유틸리티에 둔다 |
| mock 설정이 비대해질 때 | 실제 컴포넌트를 쓰는 통합 테스트로 전환한다 |
| 테스트 파일을 마칠 때 | 변이 검사를 수행한다 |

## 경고 신호

- 준비(setup)와 단언(assertion)이 같은 객체를 공유해 항상 같을 수밖에 없다
- 예외/충돌/셀렉터 실패로만 테스트가 실패할 수 있다
- 의도적인 변경마다 항상 실패하고, 실수로 인한 깨짐에는 반응하지 않는다
- 기대값이 루프/빌더/헬퍼 뒤에 숨겨져 있다
- 소스 텍스트를 grep하거나, 제거된 심볼이 계속 없는지만 확인한다
- 프레임워크만 남아도 테스트는 계속 의미 있어 보인다(즉, 자신의 코드를 검증하지 않는다)
- 커버리지를 채우기 위해 존재할 뿐 부작용/결과를 확인하지 않는다
- `*-mock` 형태의 테스트 ID를 단언하거나, mock을 제거하면 실패한다
- 어떤 메서드가 테스트 파일에서만 호출된다
- mock 설정이 테스트의 절반을 넘거나, 왜 필요한지 설명할 수 없다
- "혹시 몰라서" mock을 건다
