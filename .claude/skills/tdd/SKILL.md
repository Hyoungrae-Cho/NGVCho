# TDD(Test-Driven Development) 스킬

> 이 스킬은 [obra/superpowers](https://github.com/obra/superpowers) 저장소의 `test-driven-development` 스킬(MIT License, Copyright (c) 2025 Jesse Vincent)의 원칙을 이 프로젝트(Python 3.14/`unittest`, `detailed-design`·`implementation` 스킬)에 맞게 번역·재구성한 것이다. 세부 테스트 작성 원칙은 함께 제공되는 [writing-good-tests.md](writing-good-tests.md)를 참조한다.

## 0. 철칙(Iron Law)

```
실패하는 테스트 없이는 프로덕션 코드를 작성하지 않는다.
```

- 테스트보다 먼저 코드를 작성했다면 **삭제하고 테스트부터 다시 시작**한다. "참고용으로 남겨두기", "테스트를 작성하면서 슬쩍 맞추기"는 모두 사실상 사후 테스트(test-after)이며 허용하지 않는다.
- **규칙의 문구를 어기는 것은 규칙의 취지를 어기는 것이다.** "형식은 지켰지만 취지는 다르다"는 변명은 통하지 않는다.
- 예외(반드시 사용자 승인 필요): 일회성 프로토타입, 생성된 코드, 단순 설정 파일. 그 외 모든 신규 기능/버그 수정/리팩터링/동작 변경에는 예외 없이 적용한다.
- "이번만 TDD 생략" 이라는 생각이 들면 그 자체가 합리화 신호다(§7 참조).

## 1. RED — 실패하는 테스트 작성

1. 구현할 유닛의 함수/모듈 계약(사전조건, 사후조건, 부작용, 예외/오류 계약, 시간 제약, `detailed-design` 스킬 §4)을 확인한다.
2. 테스트 케이스를 다음 근거·기법에서 도출한다(§5의 기법 태그와 1:1 대응):
   - 동등분할(EP): 사후조건을 만족하는 대표 정상 입력
   - 경계값분석(BVA): 유효 범위의 최소/최대/경계 인접값
   - 결정테이블기반(DT): 정책 결정표(`detailed-design` §6)의 각 행(조건 조합)마다 최소 1개
   - 상태전이기반(ST): 상태전이표의 각 전이(이벤트+가드)마다 최소 1개
   - 오류추정(EG): 사전조건 위반, 오류 계약에 정의된 예외/오류 반환
3. 하나의 테스트 함수는 **하나의 행위(behavior)만** 검증한다. 테스트 이름에 "and"가 필요하면 쪼갠다.
4. 테스트를 작성하기 전에 먼저 **"이 테스트를 실패하게 만드는 프로덕션 코드 변경이 무엇인지"를 말할 수 있어야 한다**(§4.1). 말할 수 없으면 검증 대상을 다시 설계한다.
5. `unittest.TestCase`로 작성한다. 테스트 메서드명은 `test`로 시작하는 camelCase로, 행위를 설명하는 이름을 쓴다(예: `testRejectsNegativeSpeed`). 이는 `implementation` 스킬의 명명규칙과 동일한 표기법이다.
6. 각 테스트 함수에는 §5의 Doxygen 형식 설명(목적, 기법, 긍정/부정 여부)을 **반드시** 붙인다.
7. 기대값은 검증 대상 코드나 그 헬퍼로 계산하지 않고, **직접 손으로 도출한 리터럴/고정 픽스처**로 작성한다(§4.1의 "미러 단언" 금지).
8. mock/stub은 아키텍처 §4의 제공/요구 인터페이스, 하드웨어/통신 경계처럼 느리거나 외부에 있는 의존성에만 사용한다(§4.2).

### Verify RED — 실패를 직접 확인한다 (필수, 생략 불가)

```bash
python -m unittest <테스트모듈>.<테스트클래스>.<테스트메서드> -v
```

다음을 확인한다:
- 테스트가 **실패**하는가(에러/오탈자로 인한 실패가 아니라 "테스트로서" 실패인가)
- 실패 메시지가 예상한 이유(기능 미구현)와 일치하는가

테스트가 처음부터 통과한다면 이미 존재하는 동작을 검증한 것이다 — 테스트를 고친다. 임포트 오류/문법 오류로 실패한다면 그 오류를 고친 뒤 다시 실행해 "올바른 이유로" 실패하는지 확인한다.

## 2. GREEN — 통과시키는 최소 구현

1. 해당 테스트를 통과시키는 데 필요한 **최소한의 코드**만 작성한다. 아직 요구되지 않은 옵션/매개변수를 미리 만들지 않는다(YAGNI).
2. 다른 코드를 리팩터링하거나 "개선"하지 않는다 — 이 테스트를 통과시키는 것에만 집중한다.

### Verify GREEN — 통과를 직접 확인한다 (필수, 생략 불가)

```bash
python -m unittest discover
```

다음을 확인한다:
- 새 테스트가 통과하는가
- 기존 테스트가 모두 통과하는가(회귀 없음)
- 출력이 깨끗한가(에러/경고 없음)

새 테스트가 실패하면 코드를 고친다(테스트를 고치지 않는다). 기존 테스트가 실패하면 그 자리에서 바로 고친다.

## 3. REFACTOR — 구조 정리와 품질 게이트

1. 테스트가 모두 통과하는 상태를 유지하면서 중복 제거, 이름 개선, 책임 분리를 수행한다. 이 단계에서 새로운 동작을 추가하지 않는다.
2. `implementation` 스킬 §2의 품질 지표(함수 라인수 ≤50, 순환복잡도 ≤10, 중복 7라인 이하, Doxygen 주석 20% 이상, 명명규칙)를 재측정한다. 위반이 있으면 다음 사이클로 넘어가지 않고 그 자리에서 해소한다.
3. 리팩터링 중 한 번이라도 테스트가 실패하면 즉시 직전 통과 상태로 되돌리고 더 작은 단계로 나누어 다시 진행한다.
4. 리팩터링이 끝나면 전체 테스트를 다시 실행해 최종적으로 모두 통과함을 확인한 뒤 다음 사이클(RED)로 진행한다.

## 4. 좋은 테스트의 원칙

세부 규칙과 예시는 [writing-good-tests.md](writing-good-tests.md)에 있다. 핵심만 요약한다.

### 4.1 깨지는 지점을 명시한다(Name the Break)
- 테스트 본문을 쓰기 전에 "이 테스트를 실패하게 만드는 프로덕션 코드 변경이 무엇인가"를 먼저 답한다. 답할 수 없으면 관찰 가능한 행위 중심으로 다시 설계한다.
- 기대값은 검증 대상 코드나 그 헬퍼로 계산하지 말고 손으로 도출한 리터럴로 작성한다("미러 단언" 금지).
- 의도적 설계 결정(상수값, 정확한 문구, 내부 구조)만 깨지는 테스트는 변경감지기(change detector)이며 버그는 잡지 못한다 — 그 결정에 의존하는 동작을 검증한다.

### 4.2 진짜 대상을 검증한다(Exercise the Real Thing)
- mock 자체의 존재/호출 여부만 단언하지 않는다 — 실제 컴포넌트의 동작을 단언한다.
- mock으로 대체하기 전에 실제 메서드의 부작용을 모두 파악하고, 느리거나 외부에 있는 지점만 mock한다.
- mock 응답은 실제 구조를 빠짐없이 그대로 반영한다(일부 필드만 채운 mock은 통합 시 조용히 깨진다).
- 테스트 전용 정리(cleanup) 코드는 프로덕션 클래스가 아니라 테스트 유틸리티에 둔다.

### 4.3 변이 검사(Mutation Check)
- 테스트를 마치기 전에 프로덕션 코드를 머릿속으로 변이시켜 본다(잘못된 상수/분기, 누락된 상태변경/부작용, 빈 값 반환, 경계값 검증 누락 등). 각 변이마다 최소 하나의 테스트가 실패해야 한다.
- 아무 테스트도 잡아내지 못하는 변이가 있다면 그 동작은 검증되지 않은 것이거나, 테스트가 항상 통과하는 무의미한(tautological) 테스트다.

## 5. 테스트 기법·케이스 유형·Doxygen 문서화 — **필수**

모든 테스트 함수에는 **사용한 테스트 기법**, **긍정/부정 케이스 여부**, **Doxygen 형식의 테스트 목적 설명**을 반드시 포함한다. `implementation` 스킬 §4의 Doxygen 규칙을 테스트 코드에도 동일하게 적용하되, 다음 전용 태그를 추가한다.

| 태그 | 의미 |
|---|---|
| `@brief` | 이 테스트가 검증하는 행위를 한 문장으로 서술 |
| `@technique` | 사용한 테스트 기법: `EP`(동등분할) / `BVA`(경계값분석) / `DT`(결정테이블기반) / `ST`(상태전이기반) / `EG`(오류추정) 중 하나 이상 |
| `@case` | `positive`(정상 동작 기대) 또는 `negative`(예외/오류 동작 기대) |
| `@pre` | 테스트 입력이 만족/위반하는 사전조건(상세설계 함수 계약과 대응) |
| `@expected` | 기대하는 결과(반환값/예외/부작용) |

### 예시

```python
class SpeedControllerTest(unittest.TestCase):

    ## @brief 음수 속도 입력 시 ValueError를 발생시키는지 검증한다.
    ## @technique EG(오류추정) - 사전조건 위반 케이스
    ## @case negative
    ## @pre speed < 0 (사전조건 위반)
    ## @expected ValueError("speed must be non-negative") 발생
    def testRejectsNegativeSpeed(self):
        with self.assertRaises(ValueError):
            SpeedController().setTargetSpeed(-1)

    ## @brief 유효 범위 상한 경계값(120)에서 정상적으로 설정되는지 검증한다.
    ## @technique BVA(경계값분석)
    ## @case positive
    ## @pre 0 <= speed <= 120
    ## @expected getTargetSpeed()가 120을 반환
    def testAcceptsUpperBoundarySpeed(self):
        controller = SpeedController()
        controller.setTargetSpeed(120)
        self.assertEqual(controller.getTargetSpeed(), 120)
```

- `@technique`은 §1에서 도출한 근거와 반드시 일치해야 한다(임의로 다른 기법을 표기하지 않는다).
- 결정테이블/상태전이 기반 테스트는 `@pre`에 해당 표의 행 ID/전이 ID를 함께 표기해 `detailed-design` 산출물과의 추적성을 유지한다.
- 이 문서화는 §3 Refactor 단계의 주석 비율(20% 이상) 산정에도 포함된다.

## 6. 테스트 구조 규칙

- 테스트 파일: 구현 모듈 하나당 대응하는 테스트 모듈을 둔다(예: `speed_controller.py` → `test_speed_controller.py`).
- 테스트 간 독립성: 테스트는 실행 순서에 의존하지 않는다. 공유 가변 상태를 두지 말고, 필요한 초기화/정리는 `setUp`/`tearDown`을 사용한다.
- 각 테스트 케이스는 검증 대상 요구사항/함수 계약 ID를 `@pre`/`@expected` 또는 별도 주석으로 명시해 추적성(`implementation` 스킬 §8)을 유지한다.

## 7. 합리화 방지 — 흔한 변명과 실제

| 변명 | 실제 |
|---|---|
| "너무 단순해서 테스트 불필요" | 단순한 코드도 깨진다. 테스트는 30초면 된다. |
| "나중에 테스트 추가하겠다" | 나중에 쓴 테스트는 곧바로 통과한다 — 아무것도 증명하지 못한다. 구현을 검증하지 못하고, 잊은 경계값을 놓친다. 실패를 직접 본 적이 없다면 버그를 잡을 수 있다는 증거가 없다. |
| "이미 수동으로 확인했다" | 수동 테스트는 기록도, 재실행 방법도 없고 압박 속에서 케이스를 빼먹기 쉽다. 자동화된 테스트만 매번 동일하게 실행된다. |
| "지금까지 쓴 시간이 아깝다" | 매몰비용이다. 이미 쓴 시간은 되돌릴 수 없다 — 남는 선택은 TDD로 다시 쓰거나(신뢰 높음), 그대로 두고 테스트만 덧붙이는 것(신뢰 낮음)뿐이다. |
| "참고용으로 남기고 테스트부터 쓰겠다" | 결국 그 코드에 맞춰 테스트를 쓰게 된다 — 사후 테스트다. 삭제는 삭제다. |
| "탐색이 먼저 필요했다" | 좋다. 탐색 코드는 버리고 TDD로 다시 시작한다. |
| "테스트하기 어려우면 설계가 이상하다는 뜻" | 테스트가 어렵다는 신호를 무시하지 말고 인터페이스를 단순화한다. |
| "TDD는 느리다" | TDD가 실용적인 길이다 — 커밋 전에 버그를 잡고, 회귀를 막고, 두려움 없이 리팩터링하게 한다. "실용적" 지름길은 결국 프로덕션에서 디버깅하는 더 느린 길이다. |

## 8. 레드 플래그 — 발견하면 즉시 중단하고 다시 시작

- 테스트보다 코드를 먼저 작성했다
- 테스트가 즉시 통과한다(실패를 본 적이 없다)
- 왜 실패했는지 설명할 수 없다
- 테스트를 "나중에" 추가했다
- "이번만 예외로" 라는 생각이 든다
- "참고용으로 남기고" 또는 "기존 코드를 조금 손보고" 진행하려 한다
- `@technique`/`@case` 태그 없이 테스트를 작성했다

**위 항목 중 하나라도 해당되면: 코드를 삭제하고 TDD로 다시 시작한다.**

## 9. 완료 기준(체크리스트)

- [ ] 신규 함수/메서드마다 테스트가 존재한다
- [ ] 각 테스트가 구현 전에 실패하는 것을 직접 확인했다
- [ ] 각 테스트가 예상한 이유(기능 미구현)로 실패했다(오탈자가 아니다)
- [ ] 각 테스트를 통과시키는 최소 구현을 작성했다
- [ ] 모든 테스트가 통과한다
- [ ] 출력이 깨끗하다(에러/경고 없음)
- [ ] mock은 불가피한 경우에만 사용했고, 실제 동작을 검증한다(§4.2)
- [ ] 경계값과 오류 케이스가 포함되어 있다
