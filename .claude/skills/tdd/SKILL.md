# TDD(Test-Driven Development) 스킬

이 스킬은 `unittest`를 이용한 Red-Green-Refactor 절차를 규정한다. `implementation` 스킬(구현 단계 품질 지표)과 함께 사용하며, **테스트보다 먼저 프로덕션 코드를 작성하지 않는다.**

## 0. 원칙

- 실패하는 테스트가 없는 상태에서 프로덕션 코드를 추가/수정하지 않는다. 예외 없이 Red → Green → Refactor 순서를 지킨다.
- 한 번의 사이클은 하나의 작은 행위(behavior) 단위로 진행한다. 여러 기능을 한 번에 구현하지 않는다.
- 테스트는 상세설계 산출물(`detailed-design` 스킬 §4 함수/모듈 계약, §6 알고리즘/정책 결정표, §6.8 상태전이)을 근거로 도출한다. 근거 없이 임의의 테스트를 만들지 않는다.

## 1. Red — 실패하는 테스트 작성

1. 구현할 유닛의 함수/모듈 계약(사전조건, 사후조건, 부작용, 예외/오류 계약, 시간 제약)을 확인한다.
2. 테스트 케이스를 다음 근거에서 도출한다:
   - 정상 케이스: 사후조건을 만족하는 대표 입력
   - 경계값 케이스: 유효 범위의 최소/최대/경계 인접값
   - 예외 케이스: 사전조건 위반, 오류 계약에 정의된 오류 반환/예외
   - 정책 의사결정표가 있는 유닛: 표의 각 행(조건 조합)마다 최소 1개 테스트
   - 상태전이가 있는 유닛: 각 전이(이벤트+가드)마다 최소 1개 테스트
3. `unittest.TestCase`로 테스트를 작성한다. 테스트 메서드명은 `test`로 시작하는 camelCase로 작성한다(예: `testRejectsNegativeSpeed`). 이는 구현 코드의 명명규칙(`implementation` 스킬 §4)과 동일한 표기법을 사용한다.
4. 테스트를 실행해 **의도한 이유로 실패하는지** 확인한다(임포트 오류/문법 오류로 실패하는 것은 무효). 실패 사유가 다르면 테스트나 스텁을 수정한다.
5. 하나의 테스트 메서드는 하나의 행위만 검증한다. 여러 행위를 한 테스트에 묶지 않는다(단, 하나의 행위에 대한 여러 단언(assert)은 허용된다).

## 2. Green — 테스트를 통과시키는 최소 구현

1. 해당 테스트를 통과시키는 데 필요한 **최소한의 코드**만 작성한다. 아직 요구되지 않은 기능을 미리 만들지 않는다(YAGNI).
2. 구현 후 전체 테스트 스위트를 실행해 기존 테스트가 회귀되지 않았는지 확인한다.
3. 이 단계에서는 품질 지표(함수 라인수/순환복잡도 등, `implementation` 스킬 §2)를 아직 만족하지 않아도 된다 — 다음 Refactor 단계에서 정리한다.

## 3. Refactor — 구조 정리와 품질 게이트

1. 테스트가 모두 통과하는 상태를 유지하면서 중복 제거, 이름 개선, 책임 분리를 수행한다.
2. `implementation` 스킬 §2의 품질 지표(함수 라인수 ≤50, 순환복잡도 ≤10, 중복 7라인 이하, Doxygen 주석 20% 이상, 명명규칙)를 재측정한다. 위반이 있으면 다음 사이클로 넘어가지 않고 그 자리에서 해소한다.
3. 리팩터링 중 한 번이라도 테스트가 실패하면 즉시 직전 통과 상태로 되돌리고 더 작은 단계로 나누어 다시 진행한다.
4. 리팩터링이 끝나면 전체 테스트를 다시 실행해 최종적으로 모두 통과함을 확인한 뒤 다음 사이클(Red)로 진행한다.

## 4. 테스트 구조 규칙

- 테스트 파일: 구현 모듈 하나당 대응하는 테스트 모듈을 둔다(예: `speed_controller.py` → `test_speed_controller.py`).
- 테스트 간 독립성: 테스트는 실행 순서에 의존하지 않는다. 공유 가변 상태를 두지 말고, 필요한 초기화/정리는 `setUp`/`tearDown`을 사용한다.
- 목(Mock)/스텁: 외부 인터페이스(아키텍처 §4 제공/요구 인터페이스, 하드웨어/통신 경계)에 대해서는 `unittest.mock`으로 대체하고, 유닛 자체의 로직만 격리 검증한다.
- 각 테스트 케이스는 검증 대상 요구사항/함수 계약 ID를 주석 또는 docstring에 명시해 추적성(`implementation` 스킬 §8)을 유지한다.

## 5. 완료 기준

- 계획된 함수/모듈 계약의 모든 정상/경계/예외 케이스, 결정표 행, 상태전이에 대응하는 테스트가 존재하고 모두 통과한다.
- 마지막 Refactor 이후 재측정한 품질 지표가 모두 기준을 만족한다.
- 위 두 조건이 만족되지 않으면 해당 유닛의 구현이 완료된 것으로 보고하지 않는다.
