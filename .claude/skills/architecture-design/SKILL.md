# 아키텍처 설계(Architecture Design) 스킬

이 스킬은 ISO 26262-6:2018 clause 7(소프트웨어 아키텍처 설계)과 Automotive SPICE 4.1 SWE.2(소프트웨어 아키텍처 설계)/SYS.3(시스템 아키텍처 설계)를 동시에 만족하는 아키텍처를 설계·평가·문서화하기 위한 방법론을 정의한다.

## 1. 아키텍처 설계 원칙 (ISO 26262-6 clause 7 / A-SPICE SWE.2, SYS.3)

### 1.1 ISO 26262-6 원칙
| 원칙 | 내용 |
|---|---|
| 계층적 분해 | 시스템 → 컴포넌트 → 유닛까지 계층 구조로 분해하고, 각 계층에서 정적/동적 관점을 모두 기술한다 |
| 적절한 분할 크기 | 하나의 컴포넌트가 과도하게 크거나 복잡해지지 않도록 크기를 제한한다 |
| 높은 응집도 | 각 컴포넌트/유닛 내부는 하나의 명확한 책임을 갖도록 설계한다(§2) |
| 낮은 결합도 | 컴포넌트 간 결합은 정의된 인터페이스로만 제한한다(§2, §4) |
| 동적/정적 행위 기술 | 표기법은 인터페이스 기술, 동적 행위 기술, 검증 용이성을 모두 지원해야 한다 |
| 오류 검출·처리 | ASIL에 따라 범위 검사, 타당성 검사, 다양성/이중화 기반 오류 검출, 복구·성능저하(degradation) 메커니즘을 아키텍처 수준에서 정의한다(§9 연계) |
| 표기법 엄격성 | ASIL이 높아질수록 비형식적 → 반형식적 → 형식적 표기법을 권고한다 |

### 1.2 A-SPICE SWE.2 / SYS.3 주요 Base Practice
| BP | 내용 |
|---|---|
| BP1 | 소프트웨어(시스템) 아키텍처 설계 개발 — 요구사항을 아키텍처 요소로 변환하고 요소 간 정적/동적 관계를 기술 |
| BP2 | 요구사항을 아키텍처 요소에 할당(§7 연계) |
| BP3 | 아키텍처 요소의 인터페이스 정의(§4) |
| BP4 | 동적 행위 기술(운영 모드, 인터럽트, 타이밍, 예외/오류 처리) |
| BP5 | 대안 아키텍처 평가 — 평가 기준을 정의하고 후보안을 비교(§6 연계) |
| BP6 | 요구사항 ↔ 아키텍처 요소 간 양방향 추적성 확립(§9 연계) |
| BP7 | 아키텍처와 요구사항 간 일관성 보장 |
| BP8 | 아키텍처 설계를 관련자에게 전달(리뷰/승인) |

## 2. 응집도(Cohesion)·결합도(Coupling) 원칙 — **필수 준수**

- 모든 컴포넌트는 **기능적 응집(Functional Cohesion)** 수준을 목표로 한다. 하나의 컴포넌트가 서로 무관한 책임을 동시에 갖지 않도록 분리한다.
- 컴포넌트 간 결합은 **데이터 결합(Data Coupling)** 또는 **제어 결합(Control Coupling)** 수준으로 제한하고, 다음은 금지한다:
  - 공통 결합(Common Coupling): 전역 가변 상태 공유
  - 내용 결합(Content Coupling): 다른 컴포넌트의 내부 구현/상태에 직접 접근
- 컴포넌트 간 의존은 **반드시 인터페이스를 통해서만** 이루어진다(§4). 직접 함수/필드 참조, 우회 경로는 결함으로 보고한다.
- 정적 의존성 그래프에 **순환 의존(Circular Dependency)이 존재하면 반드시 결함으로 표시**하고 계층 재구성 또는 인터페이스 도입으로 해소한다(템플릿 §5 대응).

## 3. SOLID 원칙의 아키텍처 수준 적용

| 원칙 | 아키텍처 적용 방법 |
|---|---|
| SRP (단일 책임) | 컴포넌트당 하나의 변경 이유(책임)만 갖도록 분해한다(템플릿 §4) |
| OCP (개방-폐쇄) | 변동 가능성이 높은 지점에 인터페이스/확장점을 두어, 기존 컴포넌트 수정 없이 신규 구현체 추가로 확장 가능하게 한다 |
| LSP (치환) | 동일 인터페이스의 모든 구현체는 계약(사전/사후조건, 오류 계약)을 위반하지 않고 상호 치환 가능해야 한다 |
| ISP (인터페이스 분리) | 하나의 거대 인터페이스 대신, 역할별로 작게 분리된 인터페이스를 정의한다. 사용하지 않는 오퍼레이션에 의존하게 만들지 않는다 |
| DIP (의존성 역전) | 상위 수준 컴포넌트는 하위 구현이 아닌 **추상(인터페이스)**에 의존한다. 의존 방향은 항상 안정적 추상 쪽으로 향해야 한다 |

## 4. 인터페이스 정의 규칙 — **필수**

- 모든 아키텍처 요소는 **제공 인터페이스(Provided)**와 **요구 인터페이스(Required)**를 명시적으로 정의한다. 인터페이스가 없는 컴포넌트 간 통신 경로는 허용하지 않는다.
- 인터페이스 명세는 다음을 반드시 포함한다(템플릿 §6):
  - 인터페이스 ID, 제공자/사용자 컴포넌트
  - 오퍼레이션/시그니처 또는 데이터/이벤트 스키마
  - 사전조건/사후조건, 시간 제약(주기, 타임아웃, 데드라인)
  - 오류 계약(오류 코드/예외/반환값과 처리 책임)
- 내부 인터페이스(§6.1: API/이벤트/데이터 저장소 동기화)와 외부 인터페이스(§6.2: HW/통신/UI/외부서비스 경계)를 구분하여 작성한다.
- 인터페이스 변경 시 영향받는 모든 사용자(요구 인터페이스 보유 컴포넌트)를 추적성(§9)으로 식별하고 함께 갱신한다.

## 5. 변경 유연성(Design for Change) 확보 전략

- 변동성이 높은 요구사항(§요구사항 문서의 "변경 가능성" 메모, 가변 사양, OEM/플랫폼 옵션 등)은 별도 컴포넌트 또는 전략(Strategy)/플러그인 지점으로 캡슐화한다.
- 정책(Policy, 가변적 비즈니스/제어 규칙)과 메커니즘(Mechanism, 안정적인 실행 절차)을 분리한다.
- 외부 시스템/하드웨어와의 결합은 어댑터 계층으로 격리하여, 외부 변경이 내부 도메인 로직에 전파되지 않게 한다(Anti-Corruption Layer).
- 위 전략은 §6 후보 아키텍처 비교 시 "변경 유연성" 평가 기준에 반영한다.

## 6. 후보 아키텍처 구조 제안 절차 — **필수, 사용자 선택 필요**

A-SPICE SWE.2 BP5(대안 아키텍처 평가)를 만족하기 위해, 최종 아키텍처를 확정하기 전에 **반드시 2~4개의 후보 구조를 제안**하고 사용자가 선택하게 한다. 임의로 하나를 확정하여 문서를 작성하지 않는다.

### 6.1 후보 패턴 참조표
| 패턴 | 적합 상황 | 강점 | 주의점 |
|---|---|---|---|
| 계층형(Layered) | 계층별 관심사가 명확히 분리되는 시스템(예: 애플리케이션/서비스/플랫폼/HAL) | 이해 용이, 표준화된 계층 경계 | 계층 간 누수(leaky abstraction) 방지 필요 |
| 포트-어댑터(Hexagonal/Ports & Adapters) | 외부 인터페이스(HW/통신/UI)가 자주 바뀌거나 다양한 변형이 필요한 시스템 | DIP 적용 용이, 테스트/변경 용이성 우수 | 어댑터 계층 설계 비용 증가 |
| 컴포넌트/서비스 기반(메시지 버스, Pub-Sub) | 다수 ECU/프로세스 간 비동기 통신, 느슨한 결합이 중요한 시스템 | 결합도 최소화, 컴포넌트 독립 배포/교체 용이 | 메시지 계약 관리, 타이밍 분석 복잡도 증가 |
| 파이프라인/데이터 흐름(Pipe-and-Filter) | 센서 신호처리, 데이터 변환 체인이 핵심인 시스템 | 흐름이 단순명확, 단계별 검증 용이 | 상태 공유가 필요한 경우 부적합 |
| 마이크로커널/플러그인 | 옵션/변형(Variant)이 많고 기능 확장이 빈번한 플랫폼 | OCP 적용 극대화 | 코어-플러그인 인터페이스 안정성 확보 필요 |

### 6.2 평가 기준(BP5) — 후보별로 반드시 비교
1. 응집도/결합도 적합성(§2)
2. SOLID 준수 용이성(§3)
3. 변경 유연성(§5)
4. ASIL 대응(오류 격리/검출 용이성, §1.1)
5. 통합 난이도 및 통합 순서 수립 용이성(§7)
6. 성능/자원 제약 대응(메모리, CPU, 타이밍)

### 6.3 절차
1. 대상 시스템의 요구사항(§0 선행 확인 결과)을 근거로 §6.1에서 2~4개 후보를 선정하고, 후보별로 §6.2 기준의 장단점을 표로 제시한다.
2. `AskUserQuestion`으로 사용자에게 후보를 제시하고 선택받는다. 사용자가 후보 외 다른 구조를 원하면 그 구조로 대체하되 동일하게 §6.2 기준으로 평가·기록한다.
3. 선택되지 않은 후보와 선택 이유는 템플릿 §10(품질속성 분석)에 근거 자료로 남긴다(BP5 추적성).

## 7. 컴포넌트 통합 순서 정의 규칙 (템플릿 §11 대응)

1. §5 정적 의존성 그래프를 기준으로 **위상 정렬(topological sort)**을 수행하여 기본 통합 순서(리프 컴포넌트 → 상위 컴포넌트)를 도출한다. 순환 의존이 있으면 §2 규칙에 따라 먼저 해소한다.
2. ASIL이 높은 컴포넌트, 인터페이스가 많은 컴포넌트, 아키텍처 리스크가 큰 컴포넌트는 기본 순서보다 **우선 통합**하도록 조정하고 조정 근거를 기록한다.
3. 각 통합 단계마다 다음을 명시한다: 통합 대상 컴포넌트, 필요한 스텁/드라이버, 검증할 인터페이스(§4), 회귀 시험 범위, 통과 기준.
4. 통합 순서는 §9(SWE.5) 통합 전략/시험 산출물과 연계되므로, 통합 순서 변경 시 해당 산출물도 갱신 대상임을 보고서에 명시한다.

## 9. 추적성

- 요구사항(SYS.2/SWE.1 산출물) ↔ 아키텍처 요소 ↔ 인터페이스 ↔ 상세설계/통합시험 항목 간 양방향 추적을 유지한다.
- 요구사항-분석 스킬(`requirements-engineering`)의 추적 매트릭스가 이미 존재하면 그 파일을 확장하여 아키텍처 계층 컬럼을 추가한다. 없으면 새 추적 매트릭스를 만들되 사용자에게 위치를 확인한다.
- 상위 링크(요구사항)나 하위 링크(인터페이스/통합시험)가 없는 아키텍처 요소는 고아(Orphan)로 표시하고 결함으로 보고한다.

## 10. 표준 근거 요약

- **ISO 26262-6:2018 clause 7**: 소프트웨어 아키텍처 설계는 계층적 구조, 컴포넌트/유닛 수준의 응집도·결합도 원칙, 인터페이스 기술, 동적/정적 행위 기술, ASIL 기반 오류 검출·처리 메커니즘을 포함해야 한다.
- **A-SPICE 4.1 SWE.2 / SYS.3**: 요구사항 → 아키텍처 요소 변환 → 인터페이스 정의 → 동적 행위 기술 → 대안 평가 → 요구사항 할당 → 양방향 추적성 → 일관성 확보 → 관련자 전달의 흐름을 따른다.
