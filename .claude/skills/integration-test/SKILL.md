# 소프트웨어 통합시험(Software Integration Test) 스킬

이 스킬은 ISO 26262-6:2018 clause 10(소프트웨어 통합 시험)과 Automotive SPICE 4.1 SWE.5(소프트웨어 통합 및 통합시험)를 동시에 만족하는 통합시험을 설계·실행·문서화하기 위한 방법론을 정의한다. 통합시험의 **시험 베이시스는 아키텍처 설계서(SWE.2)의 인터페이스 명세와 통합 순서**이며, 상세설계(SWE.3)의 호출관계를 커버리지 모집단으로 함께 사용한다.

## 0. 선행 산출물과 적용 템플릿 (방법론 — 존재 확인·사용자 확인은 에이전트 책임)

이 스킬은 "무엇이 입력이고 무엇을 준수해야 하는가"만 정의한다. 저장소에 실제로 있는지 확인하고 없을 때 사용자에게 묻는 절차는 `integration-tester` 에이전트의 실행 절차가 전담한다.

- **선행 산출물**: 본 프로젝트는 분석 → 설계 → 구현 → 테스트 순서를 반드시 준수한다(`CLAUDE.md`).
  - 아키텍처 설계 산출물(SWE.2) — 특히 **인터페이스 명세(TPL-SWE2-001 §6)**와 **통합 전략/순서(§11)**: 이 스킬의 시험 베이시스(§3).
  - 상세설계 산출물(SWE.3) — 모듈 분해·호출관계(TPL-SWE3-001 §2, §3): 호출 커버리지 모집단 산정에 사용.
  - 구현(Coding) 산출물 — 통합 대상 유닛의 소스코드와 단위시험 완료.
- **적용 템플릿**(저장소의 조직 표준 양식, 최우선 준수):
  - 통합전략/시험명세서: `WP_Templates/Engineering/SoftwareComponentVerificationAndIntegrationVerification/TPL-SWE5-001_SW 통합전략 및 통합시험 명세서 템플릿.docx`
  - 통합시험 케이스: `WP_Templates/Engineering/SoftwareComponentVerificationAndIntegrationVerification/TPL-SWE5-002_SW 통합시험 케이스 템플릿.xlsx` (열: Test ID, Trace, Integration Item, Stimulus, Expected Result, Technique, Automation)
  - 통합시험 결과서: `WP_Templates/Engineering/SoftwareComponentVerificationAndIntegrationVerification/TPL-SWE5-003_SW 통합시험 결과서 템플릿.xlsx` (열: Test ID, Trace, Result, Actual Result, Evidence Locator, Defect ID, Disposition / Run Summary 시트)
  - 코드 리뷰/인스펙션이 필요하면 공통 템플릿 `TPL-REV-001`(Common/SUP.1)을 사용한다.
- **산출물 형식 규칙**: `.docx`는 `anthropic-skills:docx`, `.xlsx`는 `anthropic-skills:xlsx` 스킬로 기존 구조를 유지한 채 작성한다. 파일명은 `WP_Templates/Engineering/README.md` 규칙을 따른다.

## 1. ISO 26262-6 clause 10 시험 기법 — **필수 적용**

| 기법 | 내용 | 이 프로젝트에서의 적용 근거 |
|---|---|---|
| 요구사항 기반 시험(Requirements-based Test) | 통합 대상에 할당된 요구사항으로부터 시험 케이스 도출 | 아키텍처 §12(요구사항 할당) |
| 인터페이스 시험(Interface Test) | 컴포넌트 간 제공/요구 인터페이스 계약(시그니처, 사전·사후조건, 시간 제약, 오류 계약) 검증 | 아키텍처 §6(인터페이스 명세) — **이 프로젝트의 핵심 시험 베이시스** |
| 결함 주입 시험(Fault Injection Test) | 인위적으로 오류/결함을 주입해 오류 검출·처리·복구 메커니즘이 설계대로 동작하는지 검증 | 아키텍처 §9(오류 격리와 안전 동작), ASIL이 부여된 요소에 우선 적용 |
| 자원 사용량 시험(Resource Usage Test) | 메모리, CPU, 타이밍 등 자원 제약 충족 여부 검증 | 아키텍처 §13(자원 및 배포 경계) |
| 백투백 비교 시험(Back-to-back Test) | 모델 기반 설계가 있는 경우, 모델과 코드의 동작을 비교 | 모델 기반 설계 산출물이 있을 때만 적용, 없으면 생략하고 근거를 기록 |

- 통합 단계별로 위 기법 중 해당되는 것을 모두 적용한다. 임의로 기법을 생략하면 생략 근거를 명시한다(예: 백투백 시험은 모델 기반 설계가 없어 해당 없음).
- 각 시험 케이스는 사용한 기법을 `TPL-SWE5-002`의 `Technique` 열에 명시한다.

## 2. 구조적 커버리지 목표 — **함수 커버리지·호출 커버리지 100%, 협상 불가**

ISO 26262-6 clause 10의 소프트웨어 통합시험 수준 구조적 커버리지 지표는 함수 커버리지(Function Coverage)와 호출 커버리지(Call Coverage)다. 이 프로젝트는 ASIL 등급과 관계없이 **두 지표 모두 100% 달성**을 통합시험 종료 기준으로 강제한다(§5).

| 지표 | 정의 | 목표 |
|---|---|---|
| 함수 커버리지 | 통합 범위 내 정의된 함수/메서드 중 통합시험 실행 중 최소 1회 진입한 함수의 비율 | 100% |
| 호출 커버리지 | 정적 호출 그래프(caller → callee)의 모든 호출 관계(엣지) 중 통합시험 실행 중 최소 1회 실제로 발생한 엣지의 비율 | 100% |

### 2.1 측정 방법(오픈소스 도구 기준)

1. **함수 목록/정적 호출 그래프 추출**: `ast`(표준 라이브러리) 또는 `pyan3`/`code2flow`(오픈소스)로 통합 범위 내 함수 정의 목록과 caller→callee 정적 호출 엣지 목록을 추출한다.
2. **함수 커버리지 측정**: `coverage.py`(`coverage run --branch -m unittest discover` 후 `coverage json`)의 실행 결과에서, 각 함수의 라인 범위 내에 실행된 라인이 하나 이상 있는지로 함수 진입 여부를 판정한다.
3. **호출 커버리지 측정**: 표준 라이브러리 `sys.setprofile()`(또는 `trace` 모듈)로 통합시험 실행 중 실제 발생한 caller→callee 호출 이벤트를 기록하는 계측 스크립트를 작성하고, 1에서 추출한 정적 호출 엣지 목록과 대조해 실행된 엣지 비율을 계산한다.
4. 두 지표 모두 수치를 **도구 실행 결과로 제시**한다. 추정치를 보고하지 않는다. 도구가 설치되어 있지 않으면 사용자에게 설치 여부를 확인한다.

### 2.2 미달성 처리

- 100% 미달 시 결함(커버리지 갭)으로 보고하고, 미실행 함수/호출 엣지를 식별해 해당 지점을 실행하는 통합시험 케이스를 보강한 뒤 재실행한다.
- 코드상 도달이 불가능한 방어적 분기(예: 특정 하드웨어 전용 경로)가 있다면 임의로 커버리지 목표에서 제외하지 않는다 — 근거를 문서화하고 사용자 승인을 받은 뒤에만 예외로 기록한다(템플릿 §12 적용 한계).
- 100% 미달 상태로 통합시험 완료를 보고하지 않는다.

## 3. 시험 베이시스 — 아키텍처 인터페이스와 통합 순서 — **필수**

1. 시험 설계 전에 아키텍처 설계서 §6(인터페이스 명세)과 §11(통합 전략/순서)를 반드시 `Read`한다. 아키텍처 문서 없이 임의로 통합 순서나 시험 항목을 정하지 않는다.
2. §11에 정의된 통합 순서(정적 의존성 위상 정렬 + ASIL/리스크 우선순위 조정)를 그대로 따른다. 통합 순서를 어기고(예: 하위 컴포넌트가 통합되지 않은 상태에서 상위 컴포넌트를 먼저 시험) 진행하지 않는다.
3. 각 통합 단계마다:
   - 그 단계에서 새로 결합되는 컴포넌트 쌍과 그 사이의 인터페이스(§6 내부/외부 인터페이스)를 식별한다.
   - 인터페이스 계약(ID, 오퍼레이션/데이터 스키마, 사전·사후조건, 시간 제약, 오류 계약) 항목마다 최소 1개의 인터페이스 시험 케이스를 도출한다(§1).
   - 필요한 스텁/드라이버(§11에서 정의됨)를 준비하고, 통합 단계의 진입 기준(§5)이 충족되었는지 확인한다.
4. 상세설계 §3(상세 호출관계)를 참조해 해당 통합 경계 내부의 실제 함수 호출 관계를 §2 호출 커버리지의 모집단으로 사용한다.

## 4. 시험 케이스 도출 (템플릿 §6, §7)

- **요구사항 기반**: 아키텍처 §12(요구사항 할당)에서 통합 대상에 할당된 요구사항으로부터 도출.
- **인터페이스 기반**: §3의 인터페이스 계약(정상/경계/예외 계약)으로부터 도출.
- **결함 주입 기반**: 아키텍처 §9의 오류 검출·처리·복구 메커니즘이 실제로 동작하는지 인위적 결함(예: 잘못된 입력, 통신 단절, 타임아웃)을 주입해 검증. ASIL이 부여된 요소는 반드시 포함한다.
- **자원 사용량 기반**: 아키텍처 §13의 메모리/CPU/타이밍 제약 대비 실측.
- **설계기법**: 경계값분석(BVA)/동등분할(EP)/결정테이블(DT)/상태전이(ST)를 `tdd` 스킬 §5와 동일한 기법 태그 체계로 적용해 인터페이스·시나리오 수준에서 사용한다.
- 각 케이스는 `TPL-SWE5-002`에 Test ID, Trace(요구사항/인터페이스 ID), Integration Item(통합 단계/컴포넌트), Stimulus, Expected Result, Technique, Automation 여부로 기록한다.

## 5. 진입/종료 기준, 환경 및 형상 (템플릿 §4, §5)

- **진입 기준**: 통합 대상 유닛의 구현·단위시험이 완료(Coding 산출물)되어 있고, §3에서 요구된 스텁/드라이버가 준비되어 있다.
- **종료 기준**: 해당 통합 단계에 계획된 시험 케이스가 모두 실행되어 **테스트 성공률 100%(Fail 0건)**를 달성했고(`CLAUDE.md` 통합 테스트 지침), §2의 함수/호출 커버리지가 100%(또는 승인된 예외 포함 100%)다. 실패한 시험은 코드/설계를 수정해 재시험으로 통과시키며, 실패를 승인된 이월 상태로 남겨둔 채 종료하지 않는다.
- 환경/형상: 시험 도구, 실행 환경, 소프트웨어 버전, 시험 데이터, 형상 식별 방법을 명시한다.

## 6. 회귀 전략, 실패/편차 처리 (템플릿 §9, §10)

- 코드/인터페이스 변경 시 영향받는 통합 단계와 시험 케이스를 식별해 회귀 범위를 정하고, 가능한 한 자동 실행한다.
- 시험 실패, 환경 문제, 계획 편차는 유형을 분류해 기록하고, 결함으로 연결한 뒤 재시험 및 승인 절차를 거친다. 임의로 실패를 통과 처리하지 않는다.

## 7. 추적성 (템플릿 §11, §13)

- 아키텍처 인터페이스/요구사항 ↔ 통합시험 케이스 ↔ 실행 결과 ↔ 결함 간 양방향 추적을 유지한다.
- 이전 단계(`architecture-design`/`detailed-design`/`implementation`)에서 만든 추적 매트릭스가 있으면 통합시험 컬럼을 추가해 확장한다. 없으면 위치를 사용자에게 확인한다.
- 상위 링크(인터페이스/요구사항)나 실행 결과가 없는 시험 케이스는 고아(Orphan)로 표시하고 결함으로 보고한다.

## 8. 표준 근거 요약

- **ISO 26262-6:2018 clause 10**: 소프트웨어 통합시험은 요구사항 기반/인터페이스/결함 주입/자원 사용량/백투백 시험 기법을 적용하고, 함수 커버리지·호출 커버리지 등 구조적 커버리지를 충족해야 한다.
- **A-SPICE 4.1 SWE.5**: 통합 전략(회귀 전략 포함) 수립 → 통합시험 명세 개발 → 통합 전략에 따른 소프트웨어 유닛/컴포넌트 통합 → 시험 케이스 선정 및 실행 → 아키텍처 설계 ↔ 통합시험 명세 ↔ 결과 간 양방향 추적성 확립 → 일관성 확보 → 결과 요약 및 전달의 흐름을 따른다.
