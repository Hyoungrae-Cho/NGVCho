# 구현(Implementation) 스킬

이 스킬은 `CLAUDE.md`의 구현 지침과 ISO 26262-6:2018 clause 8(소프트웨어 유닛 구현), A-SPICE 4.1 SWE.3(Unit Construction 관점)을 만족하는 코드 작성 방법을 규정한다. 구현은 상세설계(`detailed-design` 스킬, SWE.3) 산출물을 입력으로 받아 Python 3.12 소스코드와 `unittest` 기반 테스트로 실현하는 단계다.

## 0. 선행 산출물과 산출물 규칙 (방법론 — 존재 확인·사용자 확인은 에이전트 책임)

이 스킬은 "무엇이 입력이고 무엇을 만들어야 하는가"만 정의한다. 저장소에 실제로 있는지 확인하고 없을 때 사용자에게 묻는 절차, 그리고 `tdd` 스킬을 이용한 Red-Green-Refactor 실행 자체는 `Coding` 에이전트의 실행 절차가 전담한다.

- **선행 산출물**: 대상 유닛의 상세설계(SWE.3) 산출물 — 함수/모듈 계약, 공통 자료형, 알고리즘/결정표/상태전이. 본 프로젝트는 분석 → 설계 → 구현 → 테스트 순서를 반드시 준수한다(`CLAUDE.md`).
- **구현 방법**: 반드시 `tdd` 스킬의 Red-Green-Refactor 절차를 적용한다(방법론 자체는 `tdd` 스킬이 정의하며 이 스킬은 재정의하지 않는다). 실패하는 테스트 없이 프로덕션 코드를 작성하지 않는다.
- **완료 시 산출물**: 소스코드(Python 3.12)·`unittest` 테스트 코드, 품질 지표 측정 리포트(§3), 코드 리뷰/인스펙션 결과(`TPL-REV-001`, Common/SUP.1), 신규 외부/OSS 라이브러리 도입 시 `TPL-SBOM-001` 갱신, 추적 매트릭스 갱신(§8).
- **산출물 형식 규칙**: `.xlsx` 산출물은 `anthropic-skills:xlsx` 스킬로 기존 시트/열 구조를 유지한 채 작성한다. 파일명은 `WP_Templates/Engineering/README.md` 규칙(`<산출물 ID>_<산출물명>.<확장자>`)을 따른다.

## 1. 개발 환경

- 구현 언어: **Python 3.12**.
- 테스트 프레임워크: **unittest**(`tdd` 스킬 절차 참조).
- 순환복잡도, 함수 라인수 등 측정 지표는 **오픈소스 도구**로 측정한다(§3). 수치를 임의로 추정하지 않는다 — 도구 실행 결과를 근거로 제시한다.

## 2. 품질 지표 — **필수 준수, 협상 불가**

| 지표 | 기준 |
|---|---|
| 함수 라인수 | 순수코드라인(주석·공백·독스트링 제외) 50라인 이하 |
| 함수 순환복잡도(Cyclomatic Complexity) | 10 이하 |
| 중복 코드 | 최대 7라인까지 허용, 8라인 이상 동일/유사 코드 중복은 결함 |
| 주석 비율 | Doxygen 방식으로 작성하며, 전체 라인 중 20% 이상 |
| 명명규칙 | 함수명·변수명은 3글자 이상, **camelCase**(이 프로젝트는 PEP 8의 snake_case 대신 camelCase를 명시적으로 채택함 — `CLAUDE.md` 명시 지침) |
| 단위 테스트 브랜치 커버리지 | `unittest` 실행 기준 100%(`CLAUDE.md` 단위 테스트 지침) |
| 단위 테스트 성공률 | 100%(Fail 0건, `CLAUDE.md` 단위 테스트 지침) — 실패한 테스트를 남겨둔 채 완료로 보고하지 않는다 |

지표를 위반한 상태로 해당 유닛의 구현을 완료로 보고하지 않는다. `tdd` 스킬 §3(Refactor)에서 반드시 해소한다.

## 3. 측정 도구(오픈소스, Python 기준)

| 측정 대상 | 권장 도구 | 사용 방법 |
|---|---|---|
| 순환복잡도 | `radon cc <경로> -s -a` | 함수별 등급(A~F)과 복잡도 수치 확인, 10 초과 함수를 식별 |
| 함수/모듈 라인수, 주석 비율 | `radon raw <경로>` | LOC/SLOC/Comments/Multi(독스트링)를 확인하여 `(Comments + Multi) / LOC ≥ 0.2` 계산 |
| 정적분석/스타일 | `flake8`(+`mccabe` 플러그인) 또는 `pylint` | 기본 스타일 검사. **`pep8-naming` 플러그인은 snake_case를 강제하므로 이 프로젝트에는 그대로 적용하지 않는다.** camelCase·3글자 이상 규칙은 별도 정규식 검사 스크립트 또는 커스텀 pylint 체커로 검증한다(예: 함수/파라미터/지역변수명이 `^[a-z][a-zA-Z0-9]{2,}$` 패턴인지 확인) |
| 중복 코드 | `pylint`의 `duplicate-code`(symilar) 검사, 또는 `jscpd` | 7라인 초과 중복 블록 탐지 |
| 브랜치 커버리지·테스트 성공률 | `coverage run --branch -m unittest discover` + `coverage report` | 브랜치 커버리지 100%, 실행된 테스트 전체 Pass(Fail 0건)를 확인. 미달 시 §2 위반으로 처리 |

모든 지표는 `Bash`로 실제 도구를 실행한 측정값을 근거로 보고한다. 도구가 설치되어 있지 않으면 임의로 통과 처리하지 말고 사용자에게 설치 여부를 확인한다.

## 4. Doxygen 주석 규칙

- 모든 함수/클래스 상단에 `##`로 시작하는 Doxygen 스타일 블록을 작성한다.
- 최소 태그: `@brief`(요약), `@param`(각 매개변수), `@return`(반환값), 예외를 던지는 경우 `@throws`.
- 상세설계 함수 계약(사전조건/사후조건/부작용)이 있는 경우 `@pre`, `@post` 태그로 대응 관계를 명시한다.
- 주석 비율은 §3의 `radon raw` 결과로 검증하며, 20% 미만이면 설명이 필요한 지점(비자명한 분기, 단위/불변조건 등)에 주석을 보강한다. 의미 없는 채움 주석으로 비율만 맞추지 않는다.
- **테스트 코드(`unittest`)의 Doxygen 규칙은 `tdd` 스킬 §5를 따른다.** `@brief`/`@param`/`@return`/`@throws`/`@pre`/`@post`에 더해 `@technique`(사용한 테스트 기법)과 `@case`(긍정/부정 케이스 여부)를 반드시 포함한다.

## 5. 명명규칙 적용

- 함수명, 변수명, 파라미터명은 **3글자 이상**, **camelCase**로 작성한다(예: `calc`, `tmp`, `i` 같은 1~2글자 이름은 금지).
- 클래스명은 PascalCase, 모듈 파일명은 Python 관례(소문자+언더스코어)를 따르되, 모듈 내부의 함수/변수 식별자는 위 camelCase 규칙을 적용한다.
- 상수는 프로젝트에 별도 지침이 없는 한 위 규칙을 함수/변수와 동일하게 적용하고, 예외를 두는 경우 근거를 문서화한다.

## 6. 상세설계 계약 준수

- 구현은 `detailed-design` 스킬 §4(함수/모듈 계약)의 사전조건/사후조건/부작용/오류 계약/시간 제약을 그대로 반영해야 한다.
- 구현 중 계약을 변경해야 할 필요가 발견되면 임의로 코드만 바꾸지 말고, 상세설계 산출물과의 불일치를 결함으로 보고하고 상세설계 갱신 필요성을 사용자에게 확인한다.

## 7. 코드 리뷰 / 인스펙션

- 구현 단계 종료 시 `TPL-REV-001`(단계별 인스펙션 결과, Common/SUP.1)에 다음을 기록한다: 검토 대상(파일/커밋/베이스라인), 참여 역할, 진입/종료 판정, §3 측정값과 §2 기준 대비 결과, 발견된 지적사항과 조치 결과.
- 사람 리뷰어의 실제 검토가 필요한 경우, 에이전트가 자동측정 결과와 자체 점검 결과를 리뷰 초안으로 채우고, 사람 리뷰어 지정/일정은 사용자에게 확인한다. 사람 리뷰 없이 "승인" 상태로 임의 기록하지 않는다.

## 8. 추적성

- 소스 파일/함수 ↔ 상세설계 유닛 ↔ 테스트 케이스(`tdd` 스킬) 간 양방향 추적을 유지한다.
- `detailed-design` 스킬 §11에서 만든 추적 매트릭스가 있으면 소스 파일/테스트 파일 컬럼을 추가해 확장한다. 없으면 위치를 사용자에게 확인한다.
- 상위 링크(상세설계 유닛)나 하위 링크(테스트 케이스)가 없는 구현 파일/함수는 고아(Orphan)로 표시하고 결함으로 보고한다.

## 9. 외부 의존성 관리

- 구현 중 신규 외부/OSS 라이브러리를 추가하면 `TPL-SBOM-001`에 라이브러리명, 버전, 라이선스, 적용성 검토 결과를 갱신한다(`detailed-design` 스킬 §10과 동일 규칙). 라이선스가 불확실하면 임의로 도입하지 않고 사용자에게 확인한다.

## 10. 표준 근거 요약

- **`CLAUDE.md` 구현 지침**: Python 3.12, unittest, TDD, 오픈소스 측정 도구, 함수 라인수/순환복잡도/중복코드/주석비율/명명규칙 기준.
- **ISO 26262-6:2018 clause 8**: 코딩 가이드라인(낮은 복잡도 강제, 언어 서브셋/스타일 가이드 사용, 모호하지 않은 표기법)을 구현 단계에서 실제로 적용·검증해야 한다.
- **A-SPICE 4.1 SWE.3**: 상세설계 유닛을 실제 코드로 구축(Unit Construction)하고, 상세설계와의 일관성을 유지해야 한다.
